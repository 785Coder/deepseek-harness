# Agent Note: 在 JSON-RPC SDK 服务器中恢复已持久化的会话

Status: implemented

[English](2026-08-26-sdk-server-resume-sessions.md) | 中文

## 问题

JSON-RPC SDK 服务器的 `createSession` 对每个 `sessionId` 都会无条件创建一个全新的空会话，即使该 id 在磁盘上已存在持久化日志。因此，复用某会话 id 的新运行时进程会在持久化层已持有同一 id 的已提交历史时，构建出一个空会话。持久化协调器的 `adoptLivePrefix` 拒绝用空 seed 覆盖已持久化的前缀并抛出 id 冲突错误；服务器将该错误吸收进 write-behind 初始化，导致之后每次写入都被拒绝、JSONL 永不更新，而模型也看不到先前的上下文。客户端只能持久化会话的第一轮，永远无法跨进程边界恢复会话。

## 决策

在 `createSession` 中，当外围组合暴露了会话持久化后端且 `sessionId` 存在已物化的存储日志时，服务器通过 `ctx.agents.resume(...)` 恢复该会话，而不是新建一个。恢复后的 agent 会重新加载存储的历史并继续追加到同一日志，因此客户端可以在服务器重启后继续同一会话。没有存储日志的 `sessionId`，或没有持久化后端的组合，仍通过 `ctx.agents.create(...)` 创建全新会话。

存在性检查使用持久化服务的轻量级 `listSnapshots()`，它只读取头部而从不加载完整日志。服务器对 `listSnapshots` 能力做了守卫，因此那些通过 `get` 暴露其他服务的上下文绝不会被误判为持久化。

## 备选方案

**总是创建，让协调器合并或覆盖。** 拒绝：协调器的 `adoptLivePrefix` 刻意禁止用空的 live seed 覆盖已持久化的前缀，而这正是产生该 bug 的冲突。

**只要配置了持久化后端就总是恢复。** 拒绝：恢复一个没有存储日志的会话 id 会因持久化加载而失败。服务器必须先检查日志是否存在，再选择恢复路径。

## 影响

客户端现在可以跨服务器重启持久化并恢复会话：存储的历史会被重新加载进模型上下文，日志会继续追加而不是冲突。代价是每个新建会话要多做一次仅头部的持久化列表，即每次新会话 id 多一次目录遍历，而不做完整日志解析。
